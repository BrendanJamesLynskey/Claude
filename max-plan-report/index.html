A Max Plan in Place of API Calls

Running batch agent work on a Claude subscription: techniques, pros and cons
October 2026 · worked example: the CVDP RTL Agent benchmark

01Summary

A Claude Max subscription has a weekly allowance that is lost if it is not used. Metered API calls cost money per token. For batch work you run yourself (evaluations, benchmarks, bulk code changes), the unused allowance can do work that would otherwise be paid for. The supported way to do that is to run Claude Code itself, headless, as the worker, rather than trying to turn the subscription into a raw model endpoint.

Key findings

  • The pattern that works: one headless claude -p session per task, with its tools, turns and wall time capped, its transcript saved, and the result judged by something outside it (tests, a grader, a diff).
  • It runs in CI: claude setup-token issues a long-lived token for the plan, which goes into a repository secret as CLAUDE_CODE_OAUTH_TOKEN.
  • Usage is measurable: claude -p "/usage" prints the session (5-hour) and weekly percentages headless, so a script can log them while a batch runs.
  • In the worked example, 10 hardware-design tasks on Opus 5.5 took about 1% of a weekly allowance; Claude Code's own API-rate estimate for the same work was $2.31. A full four-model ladder on 86 tasks, which Claude Code estimates at about $145 at API rates, fitted into the allowance across two weeks.
  • Bigger is not always better here: Opus 5.5 solved the most (73%). Fable 5.1, the largest model, worked longest per task and ran into the per-task time cap, so its score (67%) was below Sonnet's.
  • The main cost is to the measurement: there is no billed cost per call, the worker is a whole agent rather than a model call, and plan limits can stop a batch part-way. Each needs a rule, set out in section 05.

02Two ways to try it, and the one to use

Don't: a subscription session per LLM call

Replacing each API call inside your own agent with a Claude session that receives the prompt.

  • A Claude Code session is not a plain model call: it brings its own system prompt and tools, so you get a harness inside your harness.
  • Your agent's tool definitions have to be described in text and the replies parsed, which changes the model's behaviour and adds parsing failures.
  • Hundreds of short sessions per task run into plan limits quickly.
  • It turns a consumer plan into a model backend for another system, which is the use the terms are least likely to cover.

Do: Claude Code as the whole worker

Give one headless Claude Code session the whole task and let it work with its own tools, then score what it leaves behind.

  • This is Claude Code used as Claude Code, which is what the plan is for, including headless and CI use.
  • It makes a clean comparison point: an off-the-shelf agent beside the one you built, on the same tasks and the same grader.
  • One session per task keeps the number of sessions, and the load on the limits, low.
  • Prompt caching inside Claude Code keeps the token count per turn down.

03Techniques

3.1 The headless call

Each task gets one call. The flags that matter are the output format (so the run can be audited), the caps, and the tool lists:

claude -p "$PROMPT" \
  --output-format stream-json --verbose \
  --model claude-opus-5-5 \
  --max-turns 60 \
  --permission-mode acceptEdits \
  --allowedTools Read Edit Write Glob Grep Bash \
  --disallowedTools WebFetch WebSearch Task "Bash(curl:*)" "Bash(wget:*)" "Bash(git:*)" "Bash(pip:*)"
  • stream-json gives one JSON event per line: every tool call, the served model, and a final result event with num_turns, token usage and total_cost_usd.
  • Put a wall-time limit around the process yourself (a subprocess timeout); --max-turns alone doesn't bound time.
  • Run it with the task tree as its working directory, and keep anything it must not see (hidden tests, answers) out of that tree.

3.2 Authentication in CI

claude setup-token                                   # interactive: log in, prints a long-lived token
gh secret set CLAUDE_CODE_OAUTH_TOKEN -R owner/repo  # paste it at the prompt; never echo it
  • The token starts with sk-ant-oat01-. The terminal often wraps it over two lines, and a partly copied token fails with 401 authentication_failed.
  • To diagnose a 401 without exposing the secret, log only its shape: its length, whether it has the prefix, and whether it holds whitespace.
  • Pass the token only to the step that runs Claude Code. Add it, and the pattern sk-ant-, to the redaction list and to a scan of everything uploaded as artifacts, and fail the upload if either is found.

3.3 Packaging Claude Code in a container

  • Pin the version (the installer takes one: curl -fsSL https://claude.ai/install.sh | bash -s 2.1.310) and set DISABLE_AUTOUPDATER=1, so every task in a batch runs the same Claude Code.
  • The installer puts the binary under /root/.local. If the container runs the worker as a non-root user, that user gets Permission denied: 'claude'; copy the real binary to /usr/local/bin instead of linking to it.
  • Claude Code writes its settings under $HOME. Give the worker a writable home folder if its user has none.

3.4 Reading the result

  • An API failure can look like a success. On a 401, Claude Code retries, then emits a reply whose model is <synthetic>, and a result whose subtype can still read success. Check is_error and terminal_reason (api_error) before counting a task as attempted.
  • Redact parsed values, not raw lines. A redaction pattern can swallow a quote and leave a line that is no longer JSON; parse each event, redact its values, then write it out again.
  • Record what the worker could see: a listing of the top of its working tree, saved with each result, shows that the answers weren't there.

3.5 Tracking usage while a batch runs

claude -p "/usage"
# Current session: 26% used · resets 4pm
# Current week (all models): 75% used · resets 1am
# Current week (Fable): 0% used · resets 1am
  • It runs headless, so a loop can log it every 10 minutes beside the batch's progress, and stop or warn before a limit.
  • Two limits apply: a rolling 5-hour session limit and a weekly one. The weekly limit is the one that can't be waited out; the session limit only pauses work for a few hours.
  • Some models can have their own weekly allowance. In the worked example, Fable's weekly figure was separate from the all-models one, so a Fable batch didn't draw on the shared 25%.
  • Any interactive session you run at the same time draws on the same allowance.

3.6 Planning a batch against the allowance

  1. Smoke-test first: run about 10 tasks and read the change in the weekly figure. That gives a rate per task.
  2. Scale from the smoke test: in the worked example, 10 tasks took about 1%, so 86 tasks needed about 9%.
  3. Spend the costly models first: run the large models while there is room, and use the small, cheap ones to fill what is left before the reset.
  4. Make tasks independent and resumable: a task cut off by a limit should fail with a clear reason and be rerun alone after the reset, without spoiling the rest of the batch.
  5. Mind the concurrency: the 5-hour session limit, not the weekly one, is what stops a parallel batch. Four models at four sessions each (16 at once) used about 63% of the session limit in 10 minutes, and every task still running when it reached 100% was lost. One model at two sessions ran steadily through a whole 5-hour window.
  6. Large models burn the allowance faster per task, and not always in proportion: Fable 5.1 has its own weekly bucket, and its 86 tasks used about 64 points of it, spread over two weekly resets.

05Rules that keep the results honest

  • Never report the estimate as a cost. Leave the cost field blank, keep total_cost_usd in its own field named as an estimate, and record tokens, turns and wall time.
  • Name what was measured: "Claude Code with Opus 5.5", not "Opus 5.5". Comparing it with your own agent on another model changes both the harness and the model at once.
  • Grade outside the agent, with tests it can't see, and record its view of the working tree with each result.
  • Close the side doors: deny web tools and fetching commands, audit every shell command in the transcript for hosts, URLs and fetch tools, and exclude any task that tried.
  • Keep failed calls separate from failed tasks. A task stopped by a limit or a 401 is an llm_error, rerun later; it is not a wrong answer.
  • Pin the Claude Code version, and give one run per model the noise it has: on about 90 tasks, a single run is good to about ±5 points.

06Worked example: hardware-design tasks

The CVDP RTL Agent project measures agents on 86 problems from NVIDIA's CVDP benchmark: the agent edits Verilog in a task tree, and hidden tests score the result. Its own agent runs on a cheap model through OpenRouter. A third harness option, claudecode, runs Claude Code on a Max plan instead, through the same sweep workflow, task trees and hidden tests (agent/cvdp_agent/claude_code.py).
